# 科管系统 MVP 设计决策说明

> 本文是本次提交的核心说明文档，重点回答三个问题：**为什么做这些功能、为什么暂时不做另一些功能、系统的核心设计思路是什么。**

## 1. 决策摘要

我将本次 MVP 定义为：**一个能够真实走通“申报—立项—执行—经费—成果—验收—结项”的单机构科研项目管理闭环。**

我没有把目标设定为“尽可能多地实现页面”，而是优先证明以下能力：

1. 项目生命周期可以完整流转，而不是一组互不相关的 CRUD 页面。
2. 不同角色的职责明确，权限无法通过构造请求绕过。
3. 经费、审批和项目状态之间的数据关系可靠且可追溯。
4. 系统能够低成本启动，评审者可以快速验证，而不是停留在原型图或说明文档。
5. 关键业务规则有自动化测试支撑。

因此，本次交付的优先级是：

```text
完整业务闭环
  > 状态与权限正确
  > 数据一致性和审计
  > 本地运行体验
  > 页面数量和视觉特效
```

这是本项目最核心的范围取舍。

---

## 2. 对业务问题的理解

题目只给出了“科研项目全生命周期管理”的方向，没有指定详细功能。我将其中最重要的问题定义为：

> 如何让科研人员、科研管理员和财务人员围绕同一个项目，在明确的权限和状态约束下完成协作，并让每个关键决定都有记录可查？

科研项目管理的核心不是静态保存一份项目信息，而是管理项目在不同阶段发生的变化：

- 科研人员提交的项目是否已经获批？
- 当前是否允许填报进度和发生支出？
- 哪些支出已经通过财务审核并计入预算？
- 验收时是否有足够的过程信息？
- 项目为什么被驳回、由谁审批、何时重新提交？

因此我选择以**项目状态机、角色权限和审计记录**作为系统骨架，再围绕这三点选择功能。

---

## 3. 为什么做这些功能

### 3.1 功能选择表

| 功能 | 为什么进入 MVP | 它验证的核心能力 |
|---|---|---|
| 登录与三类角色 | 没有身份和角色，审批、财务审核都不具备真实性 | 认证、授权、职责分离 |
| 项目申报与草稿 | 是生命周期的起点，也需要体现提交前后可编辑性的差异 | 表单校验、资源归属、状态约束 |
| 立项审批与驳回重提 | 是科研管理最重要的治理节点之一 | 审批责任、状态转换、审批留痕 |
| 项目进度填报 | 体现系统不只管理申报，还管理项目执行过程 | 过程管理、历史记录、进度约束 |
| 经费登记与财务审核 | 经费是科研项目管理的高价值信息，也是最适合验证一致性的场景 | 职责分离、金额精度、预算控制 |
| 成果登记 | 连接项目执行与验收，体现科研项目最终产出 | 多类型业务数据、项目聚合展示 |
| 验收审批与结项 | 形成完整生命周期终点 | 验收前置条件、终态只读、闭环能力 |
| 工作台与待办 | 让不同角色登录后立即看到自己需要处理的事项 | 角色化信息架构 |
| 审计日志 | 审批、经费和状态变更必须可追溯 | 责任追踪、系统可信度 |
| 演示数据与自动化测试 | 让评审者快速理解系统，并验证主流程不是只能手工演示 | 可运行性、可验证性、工程质量 |

### 3.2 为什么一定要做完整生命周期

如果只实现项目列表和增删改查，系统虽然“能运行”，但无法体现科研管理的核心复杂度。完整生命周期要求系统回答：

- 当前项目处于哪个阶段？
- 当前用户此刻能做什么？
- 哪些操作必须先完成其他条件？
- 状态改变后，原有操作是否应该被禁止？

所以本项目使用如下主流程：

```text
草稿
  ↓ 提交
待立项审批 ──驳回──→ 立项驳回 ──修改后重新提交──┐
  ↓ 通过                                         │
执行中 ←─────────────────────────────────────────┘
  ↓ 填报进度、经费和成果
待验收 ──驳回──→ 验收驳回 ──修改总结后重新提交──┐
  ↓ 通过                                         │
已结项 ←─────────────────────────────────────────┘
```

这条路径同时覆盖正常流程和驳回后的恢复流程，比单纯增加更多独立模块更能体现系统价值。

### 3.3 为什么选择三个角色

MVP 保留三种最必要的职责：

- **科研人员**：项目内容和过程数据的主要生产者。
- **科研管理员**：负责立项和验收两个关键治理节点。
- **财务人员**：独立审核支出，避免项目负责人自行确认经费。

这三个角色已经能表达“申请人不能审批自己的申请”“业务审批和财务审核职责分离”等关键规则。继续增加部门领导、专家评委、审计人员、系统管理员等角色，会显著扩大权限矩阵和演示成本，但不会增强本次 MVP 主流程的完整性。

## 4. 为什么不做这些功能

“不做”不是遗漏，而是基于交付目标、风险和验证价值做出的主动选择。

| 暂不实现 | 不做的原因 | 何时应该实现 |
|---|---|---|
| 动态审批流、多级会签、加签和转签 | 配置化流程本身就是一个大型子系统，会挤压主流程、权限和测试时间 | 不同项目类型确实存在稳定的多级审批差异时 |
| 部门树、项目成员和复杂组织架构 | MVP 用项目负责人即可验证资源归属；复杂组织会扩大数据和权限模型 | 需要跨部门协作或按机构统计时 |
| 真实附件上传 | 需要同时解决对象存储、访问控制、病毒扫描、文件版本和容量限制 | 有稳定存储服务和明确文件安全策略时 |
| 邮件、短信和企业 IM 通知 | 依赖第三方账号和网络环境，会降低本地运行的确定性 | 主流程稳定且进入真实用户试用阶段时 |
| 银行支付、发票 OCR 和外部财务集成 | 涉及真实资金、票据合规和第三方接口，不适合在没有业务边界时模拟 | 对接对象、数据契约和合规要求明确后 |
| 多租户和跨院所协作 | 题目场景是“某科研院所”，单机构模型足以验证 MVP | 产品需要服务多个独立机构时 |
| 独立 React/Vue 前端 | 会增加 API、前端状态管理、构建和鉴权复杂度，对本次业务验证收益有限 | 交互复杂度、多人前端协作或开放 API 成为主要需求时 |
| 微服务 | 当前规模下只会增加部署、事务和调试成本 | 团队、流量或领域边界要求独立部署时 |
| 生产级报表和导出 | 对演示有帮助，但不是业务闭环的必要条件 | 管理层指标和正式报表口径确认后 |
| 大模型生成审批结论 | 审批属于责任明确的高影响决策，不应交给模型代替人工 | 仅作为材料检查或摘要建议，并保留人工最终决定时 |

这些功能都不是“永远不做”，而是没有在当前阶段获得足够高的“业务价值 / 实现与风险成本”比值。

## 5. 核心设计思路

### 5.1 以状态机表达业务，而不是让页面随意修改状态

项目状态不是一个普通文本字段，而是业务规则的入口。所有状态转换集中在服务层执行：

- 草稿或立项驳回状态才能编辑申报信息。
- 只有待立项审批状态才能由科研管理员审批。
- 只有执行中项目才能新增进度、支出和成果。
- 有待审核支出时不能提交验收。
- 验收通过后进入已结项终态，所有业务数据只读。

路由不能直接给 `project.status` 赋值，必须调用业务服务。这样可以避免页面之间出现不一致，也能让测试直接验证状态转换规则。

### 5.2 权限采用“角色 + 资源归属 + 项目状态”三层判断

仅做角色判断是不够的。例如，科研人员虽然有“编辑项目”的能力，但只能编辑自己的项目，并且只能在草稿或驳回状态编辑。

因此一次操作必须同时满足：

```text
角色允许该类操作
        ＋
当前用户拥有该资源
        ＋
资源当前状态允许该操作
```

模板会隐藏不可用按钮，但这只是用户体验优化。真正的权限检查在服务端执行，所以即使手工构造 HTTP 请求也不能绕过限制。

### 5.3 以项目详情作为信息聚合中心

项目详情页集中展示：

- 申报基本信息和当前状态。
- 项目周期、负责人和编号。
- 预算、已批准支出和剩余预算。
- 历史进度。
- 经费明细及审核状态。
- 成果记录。
- 验收内容和生命周期日志。

这样设计是因为用户处理问题时的上下文通常是“这个项目现在怎样”，而不是“系统里全部进度记录怎样”。工作台负责发现待办，项目详情负责完成任务。

### 5.4 关键写操作必须可追溯

创建、提交、审批、进度填报、支出审核、成果登记和验收都会写入审计日志。审批意见单独保存在审批记录中，而不是覆盖项目上的一段文本。

这样可以回答：

- 谁执行了操作？
- 操作发生在什么时候？
- 针对哪个项目或记录？
- 当时的结论和意见是什么？

MVP 不提供修改和删除审计日志的界面，避免追溯链被普通业务操作破坏。

### 5.5 先保证确定性，再考虑智能化

题目强调 AI Native 能力，但我没有为了“带 AI”而强行增加一个不可控的聊天入口。科研管理首先需要可靠的状态、权限和数据基础；在这些基础尚未建立时，大模型生成内容只会增加不确定性。

更合适的后续 AI 场景包括：

- 申报材料完整性检查。
- 自动提取项目风险和待办摘要。
- 根据进度记录辅助整理验收材料。
- 帮助管理员发现异常预算或长期无进展项目。

这些能力应作为**辅助建议**，明确展示依据并保留人工最终决策，尤其不能自动代替立项、财务和验收审批。

## 6. 技术选型与权衡

### 6.1 为什么使用 Python 和 FastAPI

FastAPI 提供清晰的类型接口、依赖注入和测试能力，适合快速构建同时具有工程结构的 Web 应用。Python 生态也便于未来扩展数据分析和 AI 辅助能力。

### 6.2 为什么采用 Jinja2 服务端渲染

本次没有使用独立 SPA，而是由 FastAPI 和 Jinja2 统一交付页面。这样可以：

- 用一个进程启动完整系统。
- 避免前后端仓库、构建链和跨域鉴权配置。
- 减少重复的数据结构和错误处理逻辑。
- 将更多实现时间投入状态、权限、测试和数据一致性。

业务逻辑仍然与路由和模板分离，未来需要独立前端时，可以在相同服务层之上增加 JSON API。服务端渲染是本次交付策略，不是未来演进限制。

### 6.3 为什么使用 SQLite

SQLite 不需要评审者安装和配置额外数据库服务，符合“清晰、快速本地运行”的目标，同时满足数据持久化要求。

代价是 SQLite 不适合大量并发写入。正式部署应迁移 PostgreSQL，并增加 Alembic 迁移、预算审核行锁和生产备份策略。SQLAlchemy 模型避免使用 SQLite 特有语法，为后续迁移保留空间。

### 6.4 为什么暂时使用启动建表

当前版本通过 SQLAlchemy `create_all` 为全新环境建表，以降低首次运行门槛。这适用于 MVP 的空数据库启动，但不负责已有结构的增量升级。

如果进入持续迭代或生产部署，必须切换为 Alembic 版本化迁移。这是已知且被明确记录的边界，而不是把自动建表误认为生产迁移方案。

## 7. 数据一致性决策

### 7.1 金额处理

- Python 使用 `Decimal`，数据库使用定点数列，不使用浮点数。
- 拒绝 NaN、Infinity 和非正金额。
- 预算执行金额只统计财务已批准的支出。
- 财务点击通过时重新计算已批准总额，而不是相信页面提交时的余额。
- 审批后超过预算的支出会被拒绝。

正式并发环境中还应在 PostgreSQL 中对项目预算记录加行锁，或使用原子条件更新，避免两个审核请求同时通过。

### 7.2 验收前置条件

提交验收前必须满足：

- 至少存在一条项目进展，避免没有任何执行过程就直接结项。
- 不存在待审核支出，避免项目结项后经费状态继续变化。
- 验收总结达到最小信息长度。

MVP 不强制必须登记成果。原因是基础研究、终止项目或部分特殊项目未必产生可登记成果；是否达到验收要求，应由管理员结合项目类型和验收材料判断。

### 7.3 终态只读

项目一旦验收通过进入已结项状态，就不能继续新增进度、支出或成果。终态只读避免历史项目数据在验收结论形成后继续变化。

## 8. 安全设计

- 密码使用带随机盐的 PBKDF2-SHA256 哈希，不保存明文。
- Session Cookie 包含有效期并使用 HMAC 签名，同时设置 `HttpOnly` 和 `SameSite=Lax`。
- 所有业务 POST 表单校验 CSRF token。
- Jinja2 默认转义用户输入，SQLAlchemy 使用参数绑定。
- 成果链接只允许 HTTP/HTTPS 协议，避免危险协议注入。
- 所有写操作在服务端重复校验权限和项目状态。
- 错误页面不向用户暴露调用栈和内部实现细节。

生产环境还需要 HTTPS、Cookie `Secure`、集中密钥托管、登录限流、安全响应头、日志告警和依赖漏洞扫描。

---

## 9. 可验证性设计

为了让评审者不依赖作者现场操作，项目提供：

- 三类固定演示账号。
- 草稿、待审批、执行中等不同状态的种子数据。
- 一条从创建项目到验收结项的自动化流程测试。
- 角色越权测试。
- 超预算支出测试。
- 密码、Session 和 CSRF 安全测试。
- 非有限金额及危险成果链接测试。

自动化测试当前共 6 项。它们优先覆盖高风险规则，而不是只测试页面是否返回 200。

---

## 10. 已知限制

当前 MVP 的边界包括：

- 单项目只有一名负责人，没有成员协作模型。
- 使用 SQLite，主要面向单机演示和低并发场景。
- 数据库结构采用启动建表，尚未引入版本化迁移。
- 没有真实附件、消息通知和外部系统集成。
- 没有分页和大数据量查询优化。
- 演示登录未实现生产级登录失败限流。
- 本地 HTTP 环境下 Cookie 未开启 `Secure`。

这些限制不会阻断本次 MVP 的主流程，但在生产上线前必须逐项处理。

---

## 11. 如果再增加一周

下一阶段会按以下顺序投入：

1. 引入 Alembic 和 PostgreSQL，补齐并发一致性与部署配置。
2. 增加部门、项目成员和更细的资源权限。
3. 实现真实附件、对象存储、病毒扫描和文件权限。
4. 增加站内待办、邮件通知和临期提醒。
5. 增加预算科目、报表、导出和分页。
6. 补充 Playwright 浏览器端测试和 CI。
7. 在人工审批不被替代的前提下，增加材料检查、风险摘要等 AI 辅助能力。

## 12. 最终结论

本次设计的核心不是“用最少代码做一个演示页面”，而是：

> 用尽可能小的产品范围，交付一个状态可信、权限清晰、数据可追溯、能够完整运行和验证的科研项目管理闭环。

我选择实现的功能都直接服务于这个闭环；暂时不做的功能，要么依赖尚未明确的外部条件，要么会显著扩大范围但不能增强本次核心验证。这样的取舍既保证了 MVP 的完成度，也为后续向生产系统演进保留了清晰路径。
